# 01 — Content-pack architecture

Status: draft
Owner: solo
Target: ~13–17 weeks to a v1.0 covering IT + DE, A0–A2, on web + PWA

This plan refactors Maestro around **statically generated content packs**
as the single source of truth. Lessons are no longer generated at runtime by
an LLM. Instead, Claude generates banks of drills, prompts, passages, and
explanations at authoring time; the runtime picks from those banks based on
the learner's state. A runtime LLM call survives only for **grading and
mistake explanations**, and is initially served via your own API endpoint
calling Claude, with a swap-in path for on-device models later.

The same content packs power the existing web app and a future PWA / native
shell. There is no platform gating — anything that can render HTML/CSS works.

---

## 1. Context & motivation

Previous direction (now superseded): on-device LLM lesson generation on iOS
via Apple Foundation Models. Compelling but premature — it locks the product
to Apple Intelligence-capable iPhones (iPhone 15 Pro+, ~30% installed base)
and demands a much bigger content-schema and prompt-engineering investment
to make on-device generation reliable across IT and DE at A0–A2.

This pivot trades runtime generation for a **richer, hand-curated, Claude-
authored content library**, with the following wins:

- Reaches every device — web, any phone, any browser, any tablet.
- One content source feeds web + PWA + future native apps.
- Cost is predictable: Claude only runs at authoring time and at submission
  grading time. No per-lesson inference cost. No battery hit on devices.
- Quality is bounded by what you ship, not by what a small on-device model
  produces in the moment — which is a control surface you want for a tutor.
- The current FastAPI web app keeps its routing, auth, and UI; only the
  lesson-generation layer is replaced.

The cost: lessons are picked from a finite library rather than generated.
"Personalization" becomes **selection**, not generation — which turns out to
be enough for A0–A2 if the content variety per skill is high enough.

---

## 2. Goals & non-goals

**Goals**

- Author a complete A0–A2 content library for Italian and German.
- Refactor the web app so content is read from a sealed bundle (SQLite),
  not generated by Claude at request time.
- Make the web app installable as a PWA with offline support.
- Build `maestro-pack`, a Python CLI that uses Claude to draft and refresh
  content packs at authoring time, with git as the canonical store.
- Keep an LLM in the loop for **grading and explanations** at submission
  time — initially via your server calling Claude, behind an interface that
  can be swapped for on-device models later.
- Personalize via selection: weakness-weighted drills, topic preferences,
  SRS resurfacing, anti-repetition, name interpolation.

**Non-goals (v1.0)**

- B1+ content.
- Native iOS or Android apps. PWA installable on iOS Safari and Chrome
  Android is the v1.0 mobile path; native shells come later.
- Runtime lesson generation. Lessons are picked, not invented.
- Conversation mode / free-form chat (post-v1.0).
- On-device LLM for grading at launch (architecture supports it; not required).

## 3. Architecture

### Authoring time (this repo)

```
maestro/
├── packs/
│   ├── it/{skills,functions,topics,grammar,base_vocab}/   # YAML, git-versioned
│   └── de/{skills,functions,topics,grammar,base_vocab}/
├── audio/                                        # pre-rendered AAC, git LFS
├── maestro_pack/                                 # new Python package
│   ├── cli.py                                    # entry point
│   ├── schemas/                                  # Pydantic models for pack types
│   ├── generate/                                 # Claude prompts per artifact
│   │   ├── skill.py
│   │   ├── topic.py
│   │   ├── function.py
│   │   ├── drill_bank.py
│   │   ├── reading_passage.py
│   │   └── listening_dialogue.py
│   ├── validate/                                 # schema + linguistic checks
│   ├── build/                                    # YAML → SQLite bundle
│   └── audio/                                    # Azure/ElevenLabs render
└── src/maestro/                                  # existing web app, refactored
```

`maestro-pack` CLI commands:

| Command | What it does |
| --- | --- |
| `new --skill X --lang it` | Claude drafts a skill card YAML |
| `new --function X --lang it` | Claude drafts a function pack YAML |
| `new --topic X --lang it` | Claude drafts a topic pack YAML |
| `generate-drills --skill X --topic Y --count 30` | Generate a drill bank, save to YAML |
| `generate-reading --topic X --level a2 --count 5` | Generate reading passages + comp Qs |
| `generate-listening --topic X --level a2 --count 5` | Generate listening dialogues + comp Qs |
| `generate-audio --pack X` | Render audio assets via Azure/ElevenLabs |
| `validate [pack...]` | Schema + linguistic sanity (vocab realness, agreement, register) |
| `build --target sqlite --out build/maestro.db` | Produce sealed bundle |
| `diff <old> <new>` | Compare bundles for review |

### Runtime (web + PWA)

```
Browser / PWA / future native shell
├── HTML/CSS UI                     unchanged from current htmx + Jinja
├── Bundle reader                   web = server-side Python sqlite3;
│                                   PWA-offline = wa-sqlite or sql.js
├── Lesson selector                 picks next lesson + activity variants
├── Activity renderer               per-activity templates (existing)
├── Activity scorer                 rule-based for objective answers
├── LLMGrader interface             abstract; for explanations + writing
│   ├── ClaudeAPIGrader             default: POST → server → Claude
│   ├── WebAIGrader (later)         window.ai / Chrome Prompt API
│   └── NativeFMGrader (later)      Apple Foundation Models (iOS shell)
├── SRS                             unchanged SM-2 from src/maestro/vocab/srs.py
└── User state                      Mongo (server) for web; CloudKit later
```

### Data flow

```
authoring time:
  Claude API + maestro-pack CLI → packs/*.yaml → git
  packs/*.yaml + audio/ → maestro-pack build → bundle.sqlite (versioned)

runtime:
  bundle.sqlite (deployed alongside web app, served to PWA via Cache API)
    → lesson selector picks activity variants from bank
    → renderer produces page
    → user submits
    → rule-based scorer determines correctness
    → if explanation needed: LLMGrader.explain(mistake) → API → Claude
    → SRS + mastery update → Mongo
```

### LLM grading contract

A single Python interface, implemented by Claude API for v1.0:

```python
class LLMGrader(Protocol):
    async def explain_mistake(
        self,
        activity: ActivityContext,
        user_answer: str,
        correct_answer: str,
        skill: SkillRef,
        lang: Lang,
    ) -> Explanation: ...

    async def grade_writing(
        self,
        prompt: str,
        submission: str,
        rubric: WritingRubric,
        lang: Lang,
    ) -> WritingFeedback: ...
```

`ClaudeAPIGrader` calls Claude via the existing `src/maestro/llm.py` wrapper.
Later, a `WebAIGrader` (browser `window.ai`) or `NativeFMGrader` (iOS) can be
slotted behind the same interface in the client-side runtime.

### Personalization (selection-time only)

All deterministic, all in the lesson selector:

1. **Name + light interpolation**: prompt templates have `{name}` slots.
2. **Weakness-weighted drill selection**: when picking N drills from a bank
   of M, weight by `1 / (mastery_per_subskill + ε)`. Per-skill mastery is
   tracked in user state.
3. **Topic + function preference**: user picks topics/functions during
   onboarding; selector biases toward those packs.
4. **Avoid repetition + SRS resurfacing**: each drill ID is logged on use;
   selector excludes recent IDs within a window. SM-2 schedules vocab
   resurfacing in `vocab_review` activities.

## 4. Content schema (sketch)

### Skill card

```yaml
id: passato_prossimo
lang: it
level: A2
title: { en: "Past tense — passato prossimo", it: "Il passato prossimo" }
prerequisites: [present_essere_avere, gender_agreement]
sub_skills:
  - { id: aux_avere,             weight: 0.5 }
  - { id: aux_essere,             weight: 0.3 }
  - { id: irregular_participles,  weight: 0.2 }
lesson_template:
  - { kind: grammar_card, ref: grammar/passato_prossimo.md }
  - { kind: drill,        count: 6, source: drill_banks/passato_prossimo }
  - { kind: reading,      level: A2, source: topic_chosen }
  - { kind: listening,    level: A2, source: topic_chosen }
  - { kind: writing,      prompt_pool: writing_prompts/passato_prossimo }
  - { kind: vocab_review, count: 5 }
```

### Drill bank entry

```yaml
- id: pp_avere_001
  skill: passato_prossimo
  sub_skill: aux_avere
  topic_tags: [general, food]
  difficulty: 1
  type: cloze
  prompt: "Ieri ___ (mangiare) la pizza con i miei amici."
  answer: "ho mangiato"
  distractors: ["sono mangiato", "ho mangiare", "mangiavo"]
  hint: "verb: mangiare (avere aux), 1st person singular"
```

### Function pack

```yaml
id: ordering_food
lang: it
level: A1
related_skills: [present_tense, polite_expressions, articles]
dialogues: [...]
useful_phrases: [...]
practice_scenarios: [...]
```

### Topic pack

```yaml
id: italian_history
lang: it
level_floor: A1
vocab: [...]
entities: [...]
events: [...]
dialogues: [...]
reading_passages: [...]
listening_dialogues: [...]
cultural_notes: [...]
```

### Reading passage entry

```yaml
- id: hist_read_001
  topic: italian_history
  level: A2
  text_it: "Garibaldi sbarcò in Sicilia nel 1860..."
  glossary: [...]
  questions:
    - prompt: "In che anno Garibaldi sbarcò in Sicilia?"
      type: short_answer
      answer: "1860"
```

Schemas live in `maestro_pack/schemas/` as Pydantic models. The `build`
command translates YAML → SQLite tables that mirror these shapes.

## 5. Phases

### Phase 0 — Foundations & schema (1–2 weeks)

**Goal**: lock the content schema, prove the bundle pipeline.

**Scope**

- Finalize Pydantic schemas for all pack types (skill, function, topic, drill bank, reading, listening, vocab, grammar reference).
- Draft 2 IT skill cards (`saluti`, `passato_prossimo`) and 1 IT topic pack (`food`) by hand to validate the schema covers everything.
- Port one existing A0 lesson from `data/it/a0_lessons.yaml` into the new pack format — confirm it survives without TODOs.
- `maestro-pack` CLI skeleton: `validate` and `build --target sqlite` only.
- Web app: prototype a "lesson from bundle" route alongside the existing one. Read a single drill activity from the bundle SQLite, render it. Don't replace anything yet.
- Decide bundle layout (table per artifact type vs single denormalized table) — benchmark query time on a realistic bundle size (~5000 drill items).

**Exit criteria**

- One A0 lesson in new pack form renders identically (or better) than the current static version.
- Bundle build is reproducible from YAML in <30s.
- Web prototype renders a single activity from the bundle in <50ms.

**Risks**

- Schema misses something the current activity types need. Mitigation: read every activity type in `src/maestro/routes/activities.py` before locking schemas.

---

### Phase 1 — Web refactor + authoring CLI MVP (3–4 weeks)

**Goal**: web app reads content from the bundle, not from the LLM. CLI can author new content with Claude assistance.

**Scope — web**

- Replace `src/maestro/lessons/planner.py` (LLM lesson generation) with a `LessonSelector` that picks activities from the bundle based on the curriculum graph + user state.
- Refactor `src/maestro/routes/lessons.py` to call the selector instead of the planner. Lifecycle (queued → in_progress → scored → complete) stays.
- `src/maestro/routes/activities.py`: keep per-activity rendering; teach it to pull variants from the bundle instead of from generated payloads.
- Drill scoring (`drill_scoring.py`) keeps its rule-based path. No change needed.
- Add `LLMGrader` interface + `ClaudeAPIGrader` impl. Wire it into the writing-submission and mistake-explanation paths.
- Delete the LLM lesson-generation prompt code in `src/maestro/lessons/prompts.py`; keep grading prompts.
- Onboarding flow updated to capture topic + function preferences.
- Mongo stays for user state (profile, SRS, mastery, recent-IDs window). Schema gets a small migration to add topic/function preferences.

**Scope — CLI**

- `maestro-pack new --skill/--function/--topic --lang` working with Claude integration via existing `src/maestro/llm.py`.
- `maestro-pack generate-drills --skill X --count N` producing a YAML drill bank.
- `maestro-pack generate-reading` and `generate-listening`.
- `maestro-pack validate` checking: schema, vocab realness (lemma exists in base_vocab or is glossed), agreement (gender/number) heuristics, register consistency, no English bleed.
- Audio not yet wired (Phase 2 or 3).

**Scope (out)**

- PWA install / offline (Phase 4).
- On-device LLM grader (Phase 5).
- Content fill beyond what's needed to test the loop (Phase 2).

**Deliverables**

- Web app serves lessons end-to-end from the bundle for at least one IT skill in one topic.
- CLI can author a fresh skill + drill bank in under 10 minutes of human review time.
- All current LLM-generated lesson code is removed; tests pass.

**Exit criteria**

- A user can log in, complete a lesson, submit answers, get a rule-based score, and (if they make a mistake) see an LLM-generated explanation served via the API path.
- Writing submission returns rubric + comment via Claude in <10s.
- Onboarding captures topic + function preferences and selector honors them.

**Risks**

- The current `routes/activities.py` may have generation-time assumptions baked in that don't translate. Plan a discovery pass at the start of the phase.
- LLMGrader latency on writing submissions can feel slow — stream the response if the deployed Claude model supports it.

### Phase 2 — Italian content fill, A0–A2 (3–4 weeks)

**Goal**: a complete IT learner can use the app from A0 through A2 without running out of content.

**Scope**

- Skills inventory locked at start: ~25 skill cards covering A0 (greetings, articles, gender/number, pronunciation, basic verbs, numbers, days, polite expressions), A1 (regular -are/-ere/-ire conjugation, possessives, prepositions, pronouns, modal verbs, basic negation, time expressions), A2 (passato prossimo, imperfetto, futuro semplice, comparatives, reflexive verbs, condizionale presente).
- Functions inventory: ~20 communicative functions (greeting, introducing, ordering, directions, time/dates, shopping, transport, asking for help, making plans, opinions, talking about routine, past events, descriptions, future plans).
- Topic packs: 10 IT packs (food, travel, work, family, daily life, shopping, transport, history, music, cinema).
- Drill banks: ~30 drill items per skill, mixed sub-skills, varied topics. ~750 drills total.
- Reading passages: ~5 per topic pack, leveled A1 + A2. ~50 total.
- Listening dialogues: ~5 per topic pack. ~50 total. Audio pre-rendered.
- Writing prompts: ~3 per skill at the relevant level. ~75 total.
- Grammar reference markdown per skill. ~25 pages.
- Base vocab list: ~1500 IT words (A0 + A1 + A2 frequency).
- Native-speaker IT review pass (4–6 hours). Bookable mid-phase.

**Scope (out)**

- German content (Phase 3).
- PWA (Phase 4).

**Exit criteria**

- All IT content passes `maestro-pack validate` with no errors and acceptable warning count.
- An end-to-end IT learner journey (A0 → A2) is playable without "no content available" gaps.
- Native speaker has signed off on ~80% of content; outstanding issues triaged.

**Risks**

- Claude generation quality varies by topic. Mitigation: per-pack QA checklist, hand-edit pass before native review.
- Authoring throughput is the bottleneck. Mitigation: batch generation calls (`generate-drills --count 30` in one Claude turn) rather than per-item.

### Phase 3 — German content fill, A0–A2 (2–3 weeks)

**Goal**: feature-parity for German.

**Scope**

- DE inventory: equivalent skills, functions, topics. ~25 skills (greetings, articles + cases, gender/number, basic verbs, modal verbs, separable verbs, Perfekt, Präteritum, Futur, dative/accusative prepositions, Konjunktiv II for politeness, comparatives, reflexive verbs).
- DE functions: ~20 (parallel to IT).
- DE topic packs: 10 (food, travel, work, family, daily life, shopping, transport, history, music, cinema).
- DE drill banks (~750), reading (~50), listening (~50), writing (~75).
- DE base vocab list (~1500 words).
- Native-speaker DE review pass.

**Why faster than IT**: the authoring CLI, prompts, schemas, and audio pipeline are now battle-tested. Only the content changes.

**Exit criteria**: same as Phase 2, for German.

### Phase 4 — PWA polish (2 weeks)

**Goal**: web app installs and works offline on phones and desktops.

**Scope**

- Service worker that caches the app shell + bundle + audio for offline use.
- Web app manifest, icons, splash screens, install prompt.
- Bundle versioning: bundle has a build ID; service worker checks server for new builds, downloads + swaps with a "new content available" toast.
- Offline behavior: lessons fully playable without network; LLM grading queued and submitted when back online (with "explanation pending — check back when online" UX).
- Background sync to flush queued grading requests.
- Audio cached with a quota strategy (LRU eviction beyond N MB).

**Scope (out)**

- Native iOS / Android shells (post-v1.0).
- Push notifications (post-v1.0, but capture opt-in if cheap to add).

**Exit criteria**

- App installs on iOS Safari and Chrome Android with proper icon and launch.
- Going offline mid-lesson does not break the lesson.
- Coming back online flushes any pending LLM grading requests and the user sees the explanations.

**Risks**

- iOS Safari PWA storage quotas and lifecycle quirks. Mitigation: test on real iPhone Safari early, not at end of phase.
- Bundle size growth: target <80 MB total content + audio. Above that, defer some packs to lazy CDN download.

---

### Phase 5 — LLMGrader abstraction + on-device path (2 weeks)

**Goal**: the grading runtime can swap between server API and on-device, no UI change.

**Scope**

- Refactor `LLMGrader` to a client-side interface as well (currently mixed: scoring happens server-side via FastAPI). Two impls:
  - `ServerAPIGrader`: POSTs to your existing endpoint (default).
  - `WindowAIGrader`: uses `window.ai.languageModel` (Chrome Prompt API) when available.
- Capability detection on app load. Per-user setting to force one path or the other (debug-friendly).
- Prompt templates abstracted so both backends can run the same prompt; on-device prompts may need a shorter / dumber variant.
- Quality regression suite: a golden set of ~50 mistakes per language with expected explanation features (mentions the rule, identifies the wrong form, suggests the right one). Run against both backends, score with a meta-evaluator.

**Scope (out)**

- iOS native shell with Foundation Models grader (post-v1.0).
- WebGPU + WebLLM bundled-model path (post-v1.0; expensive).

**Exit criteria**

- A Chrome user on a capable device gets explanations from Gemini Nano locally; same user on Firefox gets explanations from the server.
- Quality regression suite passes for the server backend; on-device backend acceptable for ≥70% of cases, with degradation flagged in the UI ("explained locally — limited detail").

**Risks**

- Chrome Prompt API surface is still maturing. Pin to specific Chrome version range; fall back gracefully.
- Quality difference may be jarring. Mitigation: feature-flag the on-device path until quality is acceptable.

### Phase 6 — Launch (1–2 weeks)

**Goal**: ship v1.0.

**Scope**

- Friends-and-family beta (~10 users) for 1 week. Feedback triage.
- Per-language localization of the app UI (EN + IT + DE — reuse existing `src/maestro/i18n/`).
- Marketing site / landing page describing the offer.
- Public launch.
- Confirm no shadow LLM lesson-generation code paths remain.

**Exit criteria**

- Public URL live.
- v1.0 git tag.
- README updated to describe the new architecture; LICENSE confirmed; instructions for running locally.

## 7. Cross-cutting risks

- **Content authoring volume** is the dominant cost. Plan ~1500 drills + ~100 passages + ~100 dialogues per language. Throughput depends on how well the CLI prompts are tuned in Phase 0–1; budget Phase 1 generously.
- **L1 reviewers** for IT and DE: book before Phase 2 starts. Without an L1 pass, content quality will be uneven and silently wrong in ways that erode trust.
- **Grading API cost** is the recurring runtime cost. Estimate: ~1 LLM call per mistake + 1 per writing submission. ~3 mistakes per lesson average + 1 writing = ~4 calls/lesson. At ~$0.01–0.03/call, a daily user costs ~$0.40–1.20/month. Plan pricing accordingly (or accept this as a personal-project cost while users are small).
- **Bundle size** can balloon with audio. Track per-phase. Above 100 MB, split into core + downloadable packs.
- **PWA on iOS Safari** is the riskiest platform combo. Test early, not late.
