# 04 · Content pipeline and quality checks

The pipeline turns `content/*.yaml` into the content pack and enforces the course's grounding: nothing untaught, enough recycling, full syllabus coverage. It is a Python 3.12 package `itcontent` in `pipeline/`, managed with `uv`, exposing one CLI: `content` (run it as `uv run content …`; the Makefile wraps the common calls).

YAML is loaded with **ruamel.yaml in safe mode (YAML 1.2)**, so Italian `no`, `sì`, `on` and `off` stay strings. Never use PyYAML's default loader on content.

Morph-it! lines are `form<TAB>lemma<TAB>features`; for example `gattini	gattino	NOUN-M:p` or `fatto	fare	VER:part+past+s+m`.

- **Categories** include ADJ, ADV, ART, ARTPRE (articulated preposition), AUX, MOD, CAU, ASP (verbal categories), CE, CI, CON, DET-DEMO, DET-INDEF, DET-NUM-CARD, DET-POSS, DET-WH, INT, NOUN, PON, PRE, PRO-DEMO, PRO-INDEF, PRO-PERS, PRO-POSS, PRO-WH, SI, VER, WH and WH-CHE.
- **Verb features** are mood+tense+person+number (`ind+pres+3+s`, `cond+pres+1+s`, `impr+pres+2+s`, `inf`, `ger…`); clitics attached to verbs appear as extra features.
- **Encoding:** detect it (the file has historically been Latin-1) and convert to UTF-8 NFC on load. A unit test asserts that `caffè` and `perché` are found.
- Inspect the real tag strings before writing detection rules, and record any surprises in `pipeline/data/SOURCES.md`.

## Annotation

Every Italian string is annotated: text lines, exercise strings, accepted patterns (each expansion), conversation lines and titles. Which fields hold Italian is listed per format in `docs/06` (§ Which strings are Italian); the module docstring of `itcontent/annotate.py` keeps the same list. Near-miss `answer` patterns are annotated like an accepted pattern's other expansions (never as a model answer, never gated): they are often deliberately wrong Italian.

1. **Tokenise:**
   - Split on whitespace and punctuation.
   - Keep elided forms attached to the left token (`l'amica` → `l'` + `amica`; `c'è` → `c'` + `è`; `quant'è` → `quant'` + `è`; also `po'`). An apostrophe that opens a quotation, and the one that closes it, is punctuation.
   - Digits (with `.` `,` `:` between digits: `6,20`, `10:15`) become `number` tokens; text in a line's `foreign` list (one or more words, any case) becomes `foreign` tokens.
   - Allowlisted names become `name` tokens. Names match **case-sensitively** (`Rosa` is a name, `rosa` is pink). At the start of a sentence, a name that is also an item form resolves to the name unless the line's `lemmas:` says otherwise (`lemmas: {Rosa: w:rosa}`).
   - Every other character is a punctuation token. Each token keeps the text up to the next token (`trailing`), so a line re-renders exactly; the `*` markup of note fragments and table cells goes into `trailing`, never into a token.
2. **Chunks first:** match each chunk item's `match` sequences against consecutive word tokens (punctuation, names, numbers and foreign words break a match; scanning left to right, the longest match wins). Matching ignores case unless the chunk has `case_sensitive: true` (`e Lei`, `Le piace`, `Le presento`); a case-sensitive chunk still matches when its first word is capitalised at the start of a sentence (*No, sono canadese. E Lei?*). In a pattern, a personal slot is one `slot` token and may supply a chunk's last word: `abito {ME.home}` matches `c:abito` because the countries' home phrases start with *in, a, negli, nel, nei, nelle*. Tokens inside a chunk get the chunk ID, get no grammar detections, and are exempt from the morphology, construction and production-grammar checks.
3. **Lookup:** for each remaining token, find Morph-it! analyses for the surface form; a capitalised form (sentence start, formal *Lei*) also takes the lowercased form's analyses and then drops Morph-it!'s proper-noun (NPR) readings, which would otherwise win for words such as *Al* (NPR, as in Al Capone) or *Come*; allowlisted names never get here. Elided forms in a small table take the analyses of their full forms instead, because Morph-it! lists `c'` as ADV with lemma `c'`, gives `anch'` the lemma `anch'` and lacks `quant'` (`l'`→lo/la, `un'`→una (articles only), `dell'`→dello/della, `c'`→ci, `dov'`→dove, `com'`→come, `cos'`→cosa, `quant'`→quanto, `anch'`→anche, `d'`→di, `m' t' s' v'`→mi ti si vi); other elided and truncated forms (`all'`, `nell'`, `quell'`, `po'`) use Morph-it!'s own entries.
4. **Resolve items:**
   - **Item surface forms first:** a surface equal to an item's `it`, its `plural` (unless `invariable`) or one of its `forms` resolves to that item without a lemma lookup (`amica` → `w:amico`), case-insensitively. The token keeps only the Morph-it! analyses compatible with the item's POS (noun: NOUN; verb: VER, AUX, MOD, CAU, ASP; adj: ADJ; adv: ADV, WH; prep: PRE; conj: CON, WH, WH-CHE; pron: PRO, SI, CI, NE, CE, WH, WH-CHE; det: DET; num: DET-NUM-CARD, PRO-NUM; interj: INT). When none is compatible, an analysis is synthesised from the item and flagged `synthetic` (`spremuta` is only a participle of *spremere* in Morph-it!, so it gets `NOUN-F:s`).
   - Otherwise map each analysis lemma to items whose `it` equals the lemma with a compatible POS (`italiana` → lemma *italiano* → `w:italiano`).
   - **Articles** map to the grammar points `g:indefinite-article` / `g:definite-article`, and **articulated prepositions** (ARTPRE: *al, della, negli*) to `g:articulated-prepositions` / `g:articulated-prepositions-lo-gli`, not to word items; such a token's item is the point.
   - **The lexical-article rule:** an article directly before a noun item, or before an adjective and a noun item, is part of that noun until the article's own unit (*un/una*: Unit 2; *il/la/lo…*: Unit 3, the `unit` of the point in `points.yaml`, compared in `course.yaml` order): it is annotated with the noun's item and flag `lexical_article`, with no grammar detection and no requirement of its own. An allowlisted transparent noun counts as a noun item here (*il bar*, *un euro*), and the adjective may be any word Morph-it! knows only as an adjective (*un buon caffè*). From the article's unit on, normal rules apply. This is what lets Unit 0–1 texts say *la signora Rossi* and Unit 2 say *il bar*.
   - **Choosing:** the `lemmas` override comes first (the line's, or the exercise's or layout's the string belongs to; `docs/03` § Texts, § Exercises). Then `disambiguation.yaml`: a form with a context rule (`sei`, `uno`, `la le lo gli l'`) always goes through it, even with one candidate, because the rule may rule out a reading (clitic *la* before a verb is the pronoun, so it needs an item of its own). Its conditions are machine-readable (`when_any` with `prev`/`next` matchers on the nearest non-punctuation neighbour). A neighbour is matched on its **context**: the readings of the items it can still resolve to after `lemmas` and its default (compatible Morph-it! analyses, or those synthesised from the item), so a homograph it can't be never counts (the letter noun `w:o~letter` doesn't make *uno* in *Uno o due?* an article, and `w:di~letter` doesn't make *sei* in *Sei di…?* the number); a neighbour whose form has a context rule of its own keeps every candidate's readings, and one with no candidate (*euro*) or inside a chunk its Morph-it! analyses. Then the form's `default`: an item ID picks among several candidates (*a* is Unit 1's preposition `w:a`, not the letter `w:a~letter`); `{pos: […]}` keeps only those Morph-it! readings, like a rule's choice, even with one candidate (*i* stays the article and *ci* the clitic, not the letters `w:i~letter`, `w:ci~letter`, unless `lemmas` names them). Exactly one candidate left: take it. Several: an error naming the line and the candidates.
   - None: allowlisted words pass; glossed and `recognise` tokens pass (new in this step); sound-pair words pass when their exercise's `glosses` explain them; tokens of a unit title whose unit has no items file yet are *pending* (information). In an accepted pattern's other expansions (not the model answer) the token keeps its Morph-it! lemma with no item, which is fine (a warning only when it has no Morph-it! analysis either: a likely typo); an ambiguous token there is a warning. Otherwise it's an error ("untaught lemma *x*: add an item, gloss it as new in this step, or rephrase").
5. **Detect grammar:** run the rules in `content/grammar/detection.yaml` over the chosen analyses and record (point, token span). A matcher matches a token only if **every** analysis left after disambiguation matches, so an invariable noun (`caffè`, singular and plural) never counts as a plural; a matcher with `any: true` needs only one, for verb forms Morph-it! also files under another mood or as an adjective (*parliamo* is indicative, imperative and subjunctive; *finito* is a participle and an adjective). Chunk tokens, lexical articles, names, numbers, foreign tokens and punctuation get no detections and break a sequence. `detection.yaml` is engineering-owned and outside the content lead's approval, so rules can be fixed without reopening `points.yaml`; every rule needs a passing and a failing test.
6. **Write the lock file** with tokens, spans, analyses, item IDs, chunk IDs, detections and flags (format in `docs/03` § Annotation lock files). Never edit lock files by hand; run `make annotate`. Nothing is written while there are errors; `--check` also fails on lock files that are missing, stale or left over, naming each.

**Line fields that change annotation:** `foreign: [form]` (excluded from the gates, shown in italics), `gloss: {form: en}` (context glosses; keys may be several words, matched case-insensitively; a glossed token whose item is not introduced before this step, or that has no item, is *new in this step*), `lemmas: {form: item-id}`, and `recognise: [form]` for a later form the learner should only recognise here. A `recognise` token must also have a `gloss`; it gets flag 2, is exempt from the lemma, morphology and construction gates, counts toward the new-token budget and may never appear in an answer. A `gloss`, `lemmas` or `recognise` key that doesn't occur in the line is an error. Strings outside text lines take `lemmas` from their exercise (every Italian string of the exercise itself: talk and writing models and points, dictation and repeat `say`, conversation `say`, `help` and `accept`, recall answers, match sides, options, tiles, near-misses) or their real-world layout (every string of the layout); there a key must occur in at least one of those strings.

## The ten quality checks

Checks 1–5 are automatic and run in `content check` on every build. Checks 6–10 are human or learner checks that the pipeline supports with tools. Thresholds live in `content/checker.yaml`.

**Partial content.** While the course is being written, most units are incomplete. A unit is **complete** when every `lesson-K.yaml` (K = 1…`lessons` in its spec), `task.yaml` and `check.yaml` exist. Checks 3 and 4 report incomplete units as `pending` (information, never an error), and item-level errors apply only to items whose introducing lesson file exists. An item whose `lesson` doesn't exist yet, or a grammar point whose note doesn't exist yet, counts as introduced at the start of its unit (a grammar point's `unit` in `points.yaml`), with a warning when written content relies on it (one warning per missing lesson and one per unit's grammar points, listing what is used). An item whose `lesson` *is* written but doesn't introduce it (no preview batch, not glossed as new in a text step) is an error. For `u99`, final-check exercises count as unit-check exercises. With only the golden lesson written, `make check-content` must pass.

### Check 1 · Syllabus coverage (error below 100%)

For every entry in `syllabus/a1-syllabus.yaml`, find where it is **introduced**, **practised** and **assessed** (only the roles in its `roles` list, when given):

| Ref | Introduced | Practised | Assessed |
|---|---|---|---|
| `g:` / `s:` | the step that introduces it (`docs/05` § Introductions) | ≥ 1 learn exercise with it as a primary target | ≥ 1 check or final exercise with it as a primary target |
| `cd:` | its unit | ≥ 1 learn exercise tagged with it | ≥ 1 unit-check exercise tagged with it |
| `topic:` | an item with that topic introduced | an exercise whose primary target has the topic | a check exercise whose primary target has the topic |
| `kind:` / `format:` / `section:` | a written step of that kind, a learn exercise of that format, or a check section of that id with exercises | same | a check exercise of that format, or that section |
| direct `sy:` tag | first tagged step | tagged learn exercise | tagged check exercise |

An entry is satisfied in each role if any of its refs, a direct `sy:` tag, or a can-do listing the entry in its own `syllabus` is. Only written content counts: a `cd:` is introduced once a lesson of its unit is written, a `g:` or `s:` only by a written introduction (never a partial-content fallback), and placement items never count. A point with status `chunk` is practised and assessed through exercises that target a chunk that `exemplifies` it (it is never a target itself). A gap whose units (for `units: all`, any unit) are incomplete is *pending*: one pending line gives the percentage. The report lists every entry with its three locations. `syllabus_trace` in the pack stores the result. With `coverage_mode: report` (until G3) a gap is a warning showing the percentage; with `enforce` it is an error.

### Check 2 · Level gate (errors)

*Introduced* follows `docs/05` § Introductions per skill: a preview introduces read and listen (plus recall and speak where P), a text step's `new` tokens read and listen, a note its points (read; recall if P), a sounds step its sound item; an R or chunk point is also introduced by an exemplifying chunk in a preview of its own unit or by a detection in a story or listening step of its own unit. Text-level gates need an introduction for reading, model answers one for recall.

For every text and exercise at its course position *p* (unit order, then step order). **Titles** (unit, lesson, story and conversation titles) are annotated for glosses but exempt from every gate; unit titles naturally preview their unit.

- **Lemma gate:** every word token's item is introduced at or before *p*, introduced by this very step (new), allowlisted, or listed in the line's `recognise`.
- **Morphology gate:** every verb token has an analysis whose features are unlocked (`unlock` in `detection.yaml`) by a grammar point introduced at or before *p*, or by the current lesson's target point (its story comes before its note): status P or R for texts, P only for answers. Ambiguous forms pass if any analysis is unlocked; that gap is left to the critic and the content lead. Tokens inside chunks and `recognise` tokens are exempt, as are lines carrying `allow: {reason: …}`; every such line is listed in the report.
- **Construction gate:** every grammar detection belongs to a point introduced at or before *p*, or is the current lesson's target point appearing in its story before the note.
- **New-token budget:** (tokens new in this step + `recognise` tokens) / word tokens is at most `story_new_token_max` (0.05) for stories and listening and `real_world_new_token_max` (0.10) for real-world texts.
- **Chunk points stay chunks:** a detection of a point with status `chunk` outside a chunk always fails (`vorrebbe` fails, `vorrei` inside `c:vorrei` passes).
- **What else is gated:** prompts, conversation and dictation `say` lines, Italian options, match left sides, sentence-building tiles and field labels like text lines; grammar notes too (their fragments, cells and inline examples, at the note's step, where the note's own points are introduced). The new-token budget applies to every text: real-world texts use the real-world maximum, all others the story maximum. Sound-pair words are listening material glossed in place and are not gated.
- **Production gate:** the **model answer** (the first expansion of an exercise's `answer`, of a cloze gap, and of the first pattern in each conversation intent's `accept`; every `help` phrase; talk and writing `model`s) uses only items introduced for `recall` at or before *p* (the same lesson's preview counts) and only grammar points with status P. Chunk tokens are exempt from the grammar part (`vorrei` is fine in a model answer although `g:conditional-courtesy` is a chunk point). Other expansions and later patterns are not gated: they exist to accept correct answers and may use later words; the linter only warns about tokens that have neither a Morph-it! analysis nor an item (likely typos).

### Check 3 · Recycling and balance (warnings unless stated)

- **Encounters:** occurrences of each item in texts and exercise strings from its introduction to course end (every string the learner meets: lines, layouts, prompts, `say`, options, match sides, notes, `help`, models and model answers; a chunk counts once per occurrence). P items need ≥ 10 (error below 6); R items need ≥ 6. Judged once every unit from the item's unit to the end is complete; until then the report shows the count.
- **Retrievals in the introducing lesson:** the preview counts 2 (match, then recall or choice). Add each exercise in the lesson that has the item as a primary target, contains it in the model answer of a production format (recall, sentence building, dictation, a cloze gap, a conversation turn's first accepted expansion), or pairs it in a `match`. Repeat-after-me and text the learner only reads don't count. P items need ≥ 4 (error below 2). Judged as soon as the item's `lesson` is written.
- **Recycling:** ≥ 30% of content-word tokens (nouns, verbs, adjectives, adverbs and chunks) in each unit's lesson and task texts come from earlier units (not for the first unit).
- **Grammar spiral:** every grammar point is detected or targeted in ≥ 2 later units (Units 11–12: in the final review). Judged once every later unit is complete.
- **Strand balance:** estimated minutes per strand per unit from the durations in `checker.yaml` (steps and exercises map to strands through `strands.by_kind`; the unit check is assessment and isn't counted; a story or listening text counts its words read at `story_per_word` and heard at `audio_per_word`, a listening text twice; fluency replay is the unit's stories at `fluency_rate`). Each strand's share must be within its band in `strands.bands` (CL21): input 15–35%, output 15–35%, fluency 10–35%, language focus 15–60% in Units 0–2 and 15–50% from Unit 3. A bound is a share, or `{unit: share}` whose shares each hold from their unit on in course order; such a map starts at the course's first unit and names only its units (else an error at `checker.yaml`).
- **Story length:** within the unit spec's `words` range (non-punctuation tokens of the story's lines).

Recycling and strand balance need a complete unit; an incomplete one gets one *pending* line.

### Check 4 · Alignment (errors)

The rules about one exercise or note (tags, match targets, note examples) apply as soon as its file exists; the rules about a whole unit (can-dos, the check's four skills, notes for P points) apply to complete units, and an incomplete unit gets one *pending* line.

- Every exercise has ≥ 1 `cd:` or `sy:` tag.
- Every can-do has ≥ 1 learn exercise in its unit (lessons and task) and ≥ 1 exercise in its unit check tagged with it.
- Every unit check covers listening, reading, writing and speaking.
- Every note has ≥ 2 examples from its lesson's story (or another text of its lesson: a listening or reading text).
- Every `match` exercise has as many `targets` as `pairs` (`targets[i]` belongs to `pairs[i]`).
- Every P grammar point of a complete unit is introduced by a note (`docs/05` § Introductions).

### Check 5 · Story consistency (deterministic part)

- Every speaker exists in `story-bible.yaml`; `narrator` and `announcer` are reserved speakers that need no entry.
- Every line with `to:` has a `register` allowed by the register matrix at its step: exact pairs win over `(speaker, '*')`, which wins over `('*', addressee)`; at a row's `switch_at` step both registers are allowed, before it `register`, after it `then`. Conversation nodes may override `register` (the node where someone offers tu). A mismatch is an error.
- A (speaker, addressee) pair that no row covers in that unit is an error too (the register can't be checked: the story bible needs a row), and so are two rows at the same level that both match (same `from` and `to`, overlapping `units`).
- Conversations are between `with` and `ch:you` (`docs/06` § 12): `with` → `ch:you` must allow the conversation's `register`, and `ch:you` → `with` its `learner_register` (default: `register`), at the conversation's step; a node's `register` holds for both directions from that node on.
- Heuristic warnings: second-person-singular forms (a verb whose every reading is 2nd singular, *tu, ti, te, tuo, tua, tuoi, tue*) in a `lei` line; *Lei, Suo, Sua, Suoi, Sue*, and *La, Le* inside a sentence or a chunk, in a `tu` line. In a conversation, the character's `say` lines use the character's register at their node, and the learner's `help` chips and model answers the learner's.
- The rest (ages, relationships, places, timeline, prices that must match a menu) is checked by the **content-critic** subagent (`.claude/agents/content-critic.md`) on every draft. Its report goes to `build/reports/critic/`. Trust it only after its verdicts agree with the content lead on 20–30 drafts.

### Checks 6–10 · People and learners

| # | Check | Tooling |

## Audio (`content tts`)

1. **Collect audio needs.** The pack compiler is the one place that knows what is voiced, so `content tts` and `content build` take the same needs from it (`itcontent.tts_needs`): every text with lines (one file per text; real-world layouts are not voiced), every word and chunk item (its `audio_say`, else its display form read aloud: both genders of a noun for people one after the other, a chunk's trailing `…` dropped; a form TTS would read letter by letter, like `sono nato/a`, needs `audio_say`), every sound item's pair words, and the voiced strings of exercises: dictation and repeat `say`, sound-pair words, conversation lines, a choice's `prompt_it` with `audio`, talk models, and model answers with `audio_after` (recall, sentence building, and a cloze sentence with its gap filled). Note examples play their line's segment of the text's file; generated preview exercises play their item's file. A need that can't be voiced (a speaker without a voice, a model answer with a personal slot such as `{NAME}`) is reported, never guessed.
2. **Voices** (`content/voices.yaml`): a text line uses its speaker's voice (`narrator`; `announcer`; `ch:…`; `ch:extra` picks from its pool by FNV-1a 64 of the text ID); items and sound-pair words use `items`; dictation and repeat lines the narrator; a choice's prompt the `audio.speaker` it names; conversation lines the conversation's `with`; model answers and talk models are spoken as the learner (`ch:you`). A model answer is the first expansion of its pattern, so `{m:…|f:…}` forms are said in the masculine form with the `m` voice (`docs/03`); a second, feminine rendering needs a second audio ID in the payloads and is not built yet.
3. **SSML per utterance** (one render per text line or voiced string):

   ```xml
   <speak version="1.0" xmlns="http://www.w3.org/2001/10/synthesis" xmlns:mstts="https://www.w3.org/2001/mstts" xml:lang="it-IT"><voice name="it-IT-…Neural"><prosody rate="…" pitch="…">…</prosody></voice></speak>
   ```

   Words in `pronunciation.yaml` or the line's `say:` overrides get `<phoneme alphabet="ipa" ph="…">` (§ Pronunciation).
4. **Cache key:** sha256 of voice, style, rate, pitch, SSML and output format. The render cache (`itcontent.tts_cache`) keeps each render as `<key[:2]>/<key>.flac` (lossless and sample-exact, about half the size of WAV; Git LFS) next to `<key>.json` (plain Git: voice, SSML, text, sample count, the samples' sha256 and the word boundaries). Needs already cached are skipped; a render is never overwritten (anything that changes the audio changes the key). Caches: Azure renders in `content-build/tts-cache/` (committed); mock renders in `build/tts-mock-cache/` (a build output, kept as WAV: synthetic tones compress far better under Git's zlib than as FLAC); the mini pack's in `fixtures/packs/tts-cache/` (below).
5. **Render** the rest in batch jobs of at most 1,000 inputs:
   - **Azure** (`--provider azure`, the default; `itcontent.tts_azure.AzureBatchClient`): `PUT {endpoint}/texttospeech/batchsyntheses/{id}?api-version=2024-04-01` with `inputKind: SSML` and properties `outputFormat: riff-24khz-16bit-mono-pcm`, `wordBoundaryEnabled: true`, `sentenceBoundaryEnabled: true`; poll until `Succeeded` (`Failed` is an error with Azure's message); download the result ZIP from `outputs.result` (a SAS URL: the key is never sent there); check `summary.json` (an input that failed is an error naming it) and keep each `NNNN.wav` with its `NNNN.word.json` entries (`Text`, `AudioOffset` ms, `Duration` ms); delete the job. HTTP 429 and 5xx are retried after `Retry-After`. Job IDs are `italiano-<12 hex of the batch's keys>-<random>`. Tests replay recorded responses (`pipeline/tests/fixtures/azure/`); nothing in CI touches the network.
   - **Mock** (`--provider mock`, `itcontent.tts_mock`): deterministic synthetic audio offline, no keys: the same WAV format and word boundaries Azure gives (punctuation as zero-length entries, elided forms as one word), a tone burst per word whose length follows its letters and the voice's rate and whose pitch follows the voice, so the whole flow runs end to end in tests and on any machine. Dev packs use mock audio where Azure audio is missing (and say so); release packs never do.
6. **Align** the word boundaries to our tokens (`tts_azure.align`): match normalised `Text` to the line's word, name, number and foreign tokens in order, skipping punctuation entries and quotes; one boundary may cover several tokens (`quant'è` → `quant'` + `è`, split by character share) and one token several boundaries (`e-mail`). Any other mismatch is an error that names the line. This is why voiced numbers are written in words.
7. **Assemble each text in PCM** (`itcontent.audio_assets`, `audio_pcm`): lines joined with 300 ms of silence for the same speaker, 600 ms on a speaker change, plus the earlier line's `pause_ms`. `text_lines.start_ms/end_ms` and `tokens.start_ms/end_ms` (media time from the start of the file; punctuation stays null) come from sample counts. Lines in a voice with `effect: station` (the announcer) get the station effect first: band-pass 300–3400 Hz and one 35 ms echo at 25%, in pure Python with fixed coefficients, so it keeps the sample count and gives the same samples on every machine.
8. **Audio IDs:** `a:<12 hex>` of the sha256 of the assembly manifest: the encode settings and, per line, its render's sha256 and sample count, the silence before it and its effect. That identifies the assembled PCM exactly, is computed from the cache's metadata without decoding anything, and doesn't depend on the ffmpeg build. `audio.sha256` holds the full digest; `audio.voice` the voices in order of appearance (`mock:` before a mock render's voice); `audio.duration_ms` comes from sample counts.
9. **Encode once** per text and per standalone need to AAC-LC `.m4a`, 24 kHz mono, 48 kbps, with ffmpeg (`audio_pcm.ENCODE`: `-c:a aac -profile:a aac_low -b:a 48k -ar 24000 -ac 1 -map_metadata -1 -fflags +bitexact -flags:a +bitexact -use_editlist 1 -movflags +faststart`), into `build/audio/<12 hex>.m4a` (a build output reused by every build: the name is a hash of exactly what the file holds). Never concatenate encoded AAC: every join adds encoder priming and padding and the read-along drifts. The MP4 edit list skips the encoder's 1,024 priming samples, so media time 0 is the first sample of the PCM (a pipeline test decodes a file and finds a tone within 2 ms of where it is in the PCM, about 43 ms off when the edit list is ignored; `docs/09` § Encoder delay). The file name is the audio ID's 12 hex digits (`audio.file = 3f9c0e1a2b4d.m4a`); the app always reads `audio.file`.

Secrets come from the environment (`AZURE_SPEECH_KEY`, `AZURE_SPEECH_ENDPOINT`) and are never committed. `--dry-run` prints the character count (the spoken text plus the IPA of overrides; markup isn't billed) and the cost at $15 per 1M characters. HD voices can't be used: they're real-time only, and Omni variants reject `<phoneme>`. ffmpeg is needed to store and read FLAC and to encode; the pack's rows never need it.

### Pronunciation (IPA overrides, M5.4)

- `content/pronunciation.yaml` `lexicon: {word: IPA}` applies wherever the word is voiced (whole words, case-insensitive; in an elided form like `l'ancora` the part after the apostrophe); a text line's `say: {word: IPA}` applies to that line only and wins over the lexicon. Write the stress mark (`ˈ`) before the stressed syllable and `ː` for long vowels; `content tts` warns about symbols outside Italian IPA (Azure rejects unknown phones with HTTP 400) and about a `say` key that isn't a word of its line.
- **Workflow:** the audio reviewer files an `audio` comment on a line or item (review page or app) → the agent adds a `say:` to the line (one context) or a lexicon entry (every context) → `uv run content tts --show u02.l1.story#7` prints the SSML with its `<phoneme>` and shows the line is not rendered yet → `content tts --unit u02 --dry-run` shows that only the lines concerned will render (their SSML changed; nothing else did) → `content tts --unit u02` → `content review-export --unit u02 --since` for the reviewer. `content report` lists each lexicon entry with the lines it is voiced in, every line override, and any symbol that looks wrong.

### Budget (M5.4)

The bundle's audio must stay within 150 MB (ADR-17): `content build` fails above it and prints one line per build with MB now and projected per unit. `content report` shows per unit the needs, how many are voiced, the minutes, **MB now** (the files that exist), **MB written** (the written content as real speech: Azure audio as it is, other needs, mock-voiced ones included, estimated from their characters at the speaking rate and voice rate, plus gaps) and **MB projected** (plus what the unit spec still expects: each missing lesson at the course's average per written lesson, a missing task or check at the average task or check, and the items `items.new_words` still lacks at the average per item), and the course total at 48 and at 40 kbps. The speaking rate starts at 13 characters per second and is recalibrated from Azure renders once there are 500 characters of them. If Units 0–1, once rendered, still project above budget, drop the bitrate to 40 kbps (`audio_pcm.ENCODE`; every audio ID changes with it).

## Pack build (`content build`)

- Create the database from `schemas/content-pack.sql`. Insert rows sorted by primary key, then `VACUUM INTO` the destination with `journal_mode=DELETE` (the app opens it read-only).
- `meta`: `schema_version`, `pack_version` (from `course.yaml`), `content_hash`, `git_sha`, `built_with` (pipeline version), `course_id`, `locale`, `release` (0 or 1), and in dev packs `review_files` (JSON `{"<id prefix>": {"file": "content/…yaml", "hash": "<approval hash>"}}`, which the app's review mode uses to fill in a comment's file and hash). The app refuses a pack without `schema_version`, `pack_version`, `content_hash`, `course_id`, `locale` or `release`; the other keys are optional.
- Row shapes the app relies on beyond the DDL: `sounds.pairs` is `[[{"it": "pena", "audioId": "a:…" | null}, …]]`; `exercise_targets` has no order column, so a `match` exercise's target order is its payload's `targets` (`targets[i]` belongs to `pairs[i]`), which must name exactly the pairs in `exercise_targets` (the reader checks).
- Positions: `units.ord` is the unit's index in `course.yaml` (u00 = 0); every other `ord` counts from 1 (`steps.ord` within the unit, `lessons.ord` = K, `can_dos.ord`, `note_items.ord`, `text_lines.ord` = the line's `#n`, `tokens.ord` within its line). Token indices inside payloads (a note example's `highlight`) are 0-based positions in the payload's token array.
- **Pack hash:** sha256 of a canonical SQL dump of every table (rows sorted by primary key), **excluding** the `meta` keys `content_hash`, `git_sha` and `built_with`. `content_hash` stores this value. The dump is, per table in name order, a line `table(col,…)` and then each row as a JSON array. CI rebuilds the pack and compares hashes, so the committed pack can be checked for freshness.
- **Packs are build outputs, never committed.** `make pack` builds the dev pack (`meta.release = 0`, drafts included) into the bundle folder, which is gitignored; release packs are built only for archiving or TestFlight (`make pack-release`, into `build/release/`). `make archive` (owner) puts the release pack into the bundle for the archive only and restores the dev pack afterwards. Determinism is tested instead of freshness: two builds from the same input have the same `pack-hash` (pipeline tests and CI).
- Every build first runs `content lint` (any error stops it) and reads the annotation lock files: tokens come only from them, and a string whose YAML text no longer matches its lock entry stops the build ("stale: run `make annotate`"). Every payload is validated against `schemas/pack-payloads.schema.json` and every foreign key is checked before the file is written.
- Compile:
  - step and exercise payloads (pattern expansions, token arrays, audio IDs; `docs/06`);
  - unit-level steps (opener, task steps, check, fluency) in the order `docs/06` § Unit-level steps gives: the opener for every unit with a spec; conversation, talk, writing and relay steps only from a written `task.yaml`; the check only from a written `check.yaml`; fluency only when the unit has story texts;
  - `step_introduces`, `exercise_requires` and `text_requires` from the annotations (§ Requirements);
  - `item_skills` (words and chunks: the four skills, or those of a per-skill `status`; sounds: their listed skills; grammar points: `read`, plus `recall` when P) and `item_skills.scheduled` (`docs/05`);
  - `items` for grammar points from `points.yaml` (`it` and `gloss_en` = the title, `note_en` = `about`, `lesson_id` = the lesson of their first note) and `item_requires` from their `requires`;
  - `note_items` (a note may introduce several grammar points);
  - `assessments` (placement blocks and final-check sections);
  - `syllabus_trace` (filled by check 1's tracer, M1.11; empty until then);
  - generated preview exercises (`docs/06` § 1);
  - `forms`: every word token of the included files (near-misses aside), normalised, with its item (a chunk's words with the chunk, a lexical article with its article point) and Morph-it! features, plus each word item's `it`, `plural` and `forms`;
  - `steps.strand` from `checker.yaml` `strands.by_kind` (opener `input`, practice and sounds `language-focus`, check `assessment` unless it says otherwise) and `est_seconds` from its `durations_seconds` (opener 30 s; a story's words × `story_per_word` plus its questions; a conversation `conversation_turn` × the learner turns on its longest path; fluency the unit's story words × `story_per_word` / `fluency_rate`); `lessons.est_minutes` rounds its steps up; `units.est_minutes` is the spec's `est_hours` × 60.
- **Audio:** every need the compiler meets (§ Audio) is looked up in the render caches: dev builds the Azure cache, then the mock cache; `--release` the Azure cache only; `--mini` only `fixtures/packs/tts-cache/`. A need whose lines are all rendered (and, for a text, aligned) gets its audio ID in its row or payload (`texts.audio_id` and `duration_ms`, `text_lines` and `tokens` timings, `items.audio_id`, `sounds.pairs[i][j].audioId`, the exercise payload's `audioId`, `answerAudioId`, `promptAudioId`, `modelAudioId`, conversation nodes' and sound-pair words' `audioId`, generated preview exercises' `leftAudioId` and `promptAudioId`) and one `audio` row per file. These rows come from the renders' metadata only, never from encoded bytes, so the pack hash doesn't depend on the ffmpeg build. Each file is then encoded once (`build/audio/`) and only referenced audio is copied into `App/Italiano/Resources/Content/Audio/` (`Audio/` next to the pack; files nothing references are removed). Fail if the total exceeds 150 MB, and print a projection per unit (§ Audio › Budget). Dev builds warn on missing audio (one summary line counting the needs without audio by kind and reason, plus one line per need that can't be voiced or aligned) and leave its audio ID NULL (the app shows the text without a play button); they also warn when mock audio is used, and when ffmpeg is missing (the rows are written, the files are not). `--release` fails on any missing audio and on any file it can't encode.
- **Outputs:** dev builds write `App/Italiano/Resources/Content/content.sqlite`, `--release` writes `build/release/content.sqlite`, `--mini` the fixtures below; `--out PATH` overrides. The file is written through `VACUUM INTO` a temporary file and a rename, so a failed build never leaves half a pack.
- **Release mode** includes only units whose every file (unit spec, lessons, task, check, items file) is approved and that are complete (every lesson, the task and the check exist), and fails if a unit referenced in `course.yaml` falls short; the course-wide files the content lead signs off (syllabus, grammar points, story bible, countries) must be approved too. Pass `--allow-partial` to ship the longest prefix of such units, as the beta does; unapproved placement and final-check files are then left out with a warning (the final check also needs `u99` shipped). Release packs have no `review_files`.
- **`ids.lock`** records only IDs compiled by `--release` builds: units, can-dos, items and grammar points, lessons, steps, texts, notes, exercises (including generated preview exercises), characters, and task, check and assessment IDs, each as `<id> <pack version>` the first time it ships. Draft IDs may change until their file is first approved; after that an ID can only be retired (`retired.yaml`).
- **Tiny test packs:** `make mini-pack` builds `fixtures/packs/mini.sqlite` (Unit 2 Lesson 1 and its task and check) from the golden sample for app tests and previews, plus `fixtures/packs/mini-payloads.json` (`{"exercises": {id: payload}, "steps": {id: payload}, "notes": {id: body}}`, for LearningCore's decode tests on Linux). It is built from the **frozen seed course** in `fixtures/seed-course/` (`content/` as it was with only the golden lesson written; its README says when to refresh it), never from the live `content/`, so drafting lessons doesn't change it. Its catalog (units, items, grammar points, can-dos) is Units 0–2, its steps are Unit 2's and it has no assessments; it leaves out `meta.git_sha`, so the committed files change only when the seed course or the compiler does (a pipeline test fails when they are stale: run `make mini-pack`). Its audio comes from 2–3 committed mock renders in `fixtures/packs/tts-cache/` (the check's two-line audio text `u02.check.01.audio` with every word timed, the item `w:cornetto` and the dictation `u02.l1.ex13`; other needs stay null), encoded into `fixtures/packs/Audio/` (committed, a few KB each): `ITALIANO_ROOT=$PWD/fixtures/seed-course uv run --project pipeline content tts --provider mock --cache fixtures/packs/tts-cache --only u02.check.01.audio --only w:cornetto --only u02.l1.ex13` regenerates them from the seed course. The Storage tests read its timeline through `PackReader`. The freshness test compares the pack (built without encoding, so it needs no ffmpeg) and the names in `Audio/`.

### Requirements (what eligibility checks)

The build derives what each text and exercise requires, per skill, from the annotations:

- `text_requires`: `read` for every word, chunk and grammar point in the text (its lines, or every annotated layout string; titles are exempt); `listen` as well for audio-first texts (listening steps and exercises' `audio_text`). Stories are read with audio, so they require `read` only.
- `exercise_requires`: `read` for items in prompts (`prompt_it`, `context_it`), options, match left sides, sentence-building tiles, writing labels, repeat and conversation `say` (shown with the audio) and sources (the source line, or the whole source text); `listen` for items heard without text (dictation `say`, `audio_text`, sound-pair words); `recall` for items in the model answer of production formats (the first expansion of a recall answer, a cloze gap, the first sentence-building order, the first accepted expansion of each conversation intent, conversation `help` phrases, talk and writing models). The rest of a cloze sentence is `read`. Other expansions, near-misses and content-point patterns require nothing. An exercise also requires its primary targets.
- A token requires its item; a token inside a chunk requires only the chunk and a lexical article only its noun; an article or articulated preposition requires its grammar point, as does every grammar detection. Grammar points require `read` (shown or heard) or `recall` (in model answers), never `listen` or `speak`.
- Glossed new tokens and `recognise` tokens require nothing, nor does a detection that covers one; names, numbers, foreign words, punctuation and allowlisted words require nothing.
- A lesson's target grammar points (its notes' `grammar`) are excluded from the requirements of the steps of that lesson that come before the note (the story comes before the note); an exercise after the note that shows a story line as its source does require them.
- The step that introduces an item doesn't require it: LearningCore subtracts a step's `step_introduces` from what its texts and exercises require when the step is entered (`docs/05`), so the rows stay complete and a review of the same exercise needs the items introduced.
- `pipeline/tests/fixtures/expected-requirements-u02-l1.json` holds the golden lesson's rows, checked by hand.

## Approval hash

`review.hash` is the sha256 (lowercase hex) of the file's bytes after normalising line endings to LF and removing the top-level `review:` entry (its line and any indented continuation lines; blank lines and column-0 comments *between* continuation lines belong to the entry, those after it don't). Flow style (`review: {status: draft, …}`) and block style hash alike. `content approve` writes it; `content lint` fails when an approved file's hash doesn't match, so any edit to approved content is caught even if the hook was bypassed.

## How content gets made (agents draft, people decide)

1. **Sign-off (weeks 1–3):** the content lead approves `syllabus/a1-syllabus.yaml`, all `unit.yaml` specs, `grammar/points.yaml` and `story-bible.yaml`. (`grammar/detection.yaml` stays with engineering.)
2. **Item graph:** agents draft `items/uNN.yaml` from the unit specs: words by need, then frequency (`content suggest`), about 55–70 new per unit, nouns with gender and plural, false friends flagged. The content lead reviews it with the specs.
3. **Drafting:** one non-interactive drafting run per lesson file, using the `italian-content` skill. It gets the unit spec, the story bible, the allowed items and the golden sample. Parallel runs each use **their own worktree** and `content check --unit uNN`, because they would otherwise race on `content/.annotations/` and `build/reports/`.
4. **Automatic checks:** `make annotate`, then `make check-content`; failures go back to the drafter with the report.
5. **Critic:** the content-critic subagent reviews each passing draft (story bible, naturalness, register, recycling, prices); the drafter fixes.
6. **Human review:** the content lead reviews and signs off through the review loop below; the owner runs `content approve --signoff`. Then `content tts`, and the audio reviewer listens (audio comments use the same loop).
7. **Beta:** units go to the beta cohort; `content beta-import` feeds weekly fixes, and rejected answers come back to the content lead for adjudication in the review page. Reopening an approved file needs the owner.

## Content review loop (how the teacher reviews, and how feedback gets back)

The content lead never edits YAML and never needs Git. They review in two places, both producing the same **review file**, and one command brings it into the project.

### 1 · Review pages (from week 1; no app needed)

- `content review-export --specs` covers the sign-off files (syllabus, grammar points, unit specs, story bible, countries, and the content questions in `docs/13`); `content review-export --unit u02` covers a unit's items, lessons, task and check; `content review-export --assessments` covers the placement test and the final check.
- The output is **one self-contained HTML file** (styles, script and, from M5.1, audio embedded) that opens offline in any browser. The owner sends it by email or a shared folder. Audio is what `content build` would bundle for the scope (`itcontent.review_audio`): each file is embedded once, and texts, lines (their segment of the text's file), items, sound-pair words, voiced exercise strings and conversation lines get a play button.
- It shows everything a learner would meet, plus what a learner never sees at once: every story line with its English, the note, each exercise's prompt, model answer, **every accepted answer** (expanded by the grader's own expander, `itcontent.patterns`, grouped by pattern, focus parts underlined) and each near-miss with its hint, conversations as a tree of turns, and the items with gloss, gender, plural and note. Fields without a dedicated rendering are listed as they are, so the page never hides what a file says. Step headers can take comments but don't count toward progress.
- Every element has a verdict (✓ OK · ✎ Change · ? Question), a category (Italian error, unnatural, level, answer key, hint or rule, English, culture or facts, audio, other), a comment box and an optional "Suggested Italian" field. A header shows progress (reviewed / total).
- Comments save in the browser as the teacher types (local storage; some browsers don't keep it for files opened from disk, so the page warns and offers a download before closing). **Download my review** writes `review-<scope>-<date>.json` at any time, which the teacher sends back to the owner.
- After fixes, `--since` re-exports the page with each earlier comment's resolution (fixed, answered, declined with a reason) and highlights changed elements, so the teacher re-checks only those; they can reopen any comment (the new comment names it in `reopens`). An element is **changed** when its fingerprint differs from the one in the `elements` map of the latest filed review of the scope that showed it, and **new** when that review showed its file but not the element. Earlier comments come from every ledger, so a comment filed with a unit review on its unit spec also shows on the specs page; comments whose target no longer exists are listed at the end.
- When no comment is open, **Sign off** asks for the teacher's name and adds a `signoff` block with the hash of every file they reviewed. "Open" means a comment on this page that asks for a change or a question (an adjudication other than *wrong*), or a ledger comment on these files with status `open` or `owner`; the page embeds the ledger's open comments and refuses until they are resolved. A comment edited after a download gets a new `id`, so a later download never contradicts what was already filed.
- **Answers to adjudicate** (M8.3): unit and assessment pages list the beta's rejected typed answers (`content beta-import` → `rejected.json`) that no ledger comment has adjudicated and that the current key doesn't accept, most frequent first, each with its exercise's key. The teacher chooses **Accept**, **Near-miss** (with a hint; "nearly right" makes it `outcome: almost`) or **Wrong**; for a conversation turn with several intents, also which intent it belongs to.

### 2 · Review mode in the app (from M6.10)

A `Review` build (dev pack with drafts, `ITA_REVIEW_MODE = YES`, no sync or telemetry) goes to an internal TestFlight group for the teacher. It shows what the page can't: the learner's experience, timing, audio, feedback and layout.

- Every unit and step is unlocked, with a jump menu and draft badges.
- **Comment** on any step, exercise, word card or story line (long-press): the sheet fills in the target ID, the quoted text and the file hash; the teacher adds the category, the comment and a suggestion.
- **Answer key** shows every accepted answer and near-miss of the current exercise.
- **This should be accepted**, in the feedback panel after a rejected answer, files an answer-key comment with the teacher's own answer in one tap.
- **Send** uploads the comments to the endpoint (`docs/12`) when `ITA_REVIEW_URL` is set; **Export** always writes the same review file through the share sheet.
- The app keeps every comment on the device (`Application Support/Italiano/review-comments.json`), with the hash of the file version each was made on and whether Send delivered it; Send and Export don't remove them. The content lead can delete a comment that hasn't been sent; a sent one is already with the owner and stays. If the file can't be created or written, the comments screen says so at once (Export still works). A review file holds one scope, so the app writes one file per scope (the scope of each comment's file, as `content report` counts it: a unit's lessons, task, check and items file → `uNN`; unit specs, grammar points and the story bible → `specs`; the placement test and final check → `assessments`), and a second file for the same scope when a comment was made on another version of a file (after an app update). Send posts only comments not sent yet and marks them sent after a 2xx; Export always writes them all. The app never signs off (`signoff: null`) and writes `channel: app`; like the page, it writes optional fields and an empty comment as `null`.

```json
     "comment": "…", "suggestion": "…", "response": null, "at": "2026-10-20T09:15:00Z"}
  ],
  "signoff": null
}
```

A `target` is any ID from `docs/03` (item, text line `<textId>#n`, exercise, conversation node `<exerciseId>/<nodeId>`, note, step, can-do, grammar point, syllabus entry, character, country) or a path into a spec file: `uNN.<key>[i]…` into a unit spec (`u02.can_do[1]`, `u02.tasks`; the spec's check plan is `uNN.check.items`, because `uNN.check` is the check file's ID), and `story-bible.`, `countries.`, `syllabus.` or `points.` followed by a path into that file (`story-bible.places[2]`, `story-bible.registers[14]`, `countries.other`). The content questions of `docs/13` are `CQ1`, `CQ2`… with `file: docs/13-decisions.md`. `scope` is `specs`, `assessments` or `uNN`. `files` maps each file to the hash of the version shown: the approval hash, or for `docs/13-decisions.md` the sha256 of its "Content questions" section (so the decisions log can grow without making answers stale). `response` holds the learner answer behind a "This should be accepted" comment or an adjudication. `signoff` is `{name, at, files: {path: hash}}`. `verdict` is `ok | change | question`; `category` is one of `italian-error`, `naturalness`, `level`, `answer-key`, `hint-or-rule`, `english`, `culture-or-facts`, `audio`, `other` (labels: Italian error, Unnatural, Level, Answer key, Hint or rule, English, Culture or facts, Audio, Other; `itcontent.review.CATEGORIES`, the schema and the app's `ReviewComment.Category` are kept in step by a test). Optional fields, written by the page: `elements` (target → 16-hex fingerprint of every element shown, for `--since`), a comment's `reopens` (the earlier comment it reopens) and `adjudication` (`{decision: accept | near | wrong, hint, outcome: almost | null, intent, count}`; the page files *accept* and *near* as `change`, *wrong* as `ok`, all with category `answer-key`). Schema: `schemas/review-file.schema.json`.

The ledger `reviews/<scope>.yaml` (`schemas/review-ledger.schema.json`) keeps every comment of every imported review file, as filed, plus three fields:

```yaml
scope: u02
comments:
  - id: 6c1f…                                  # … every field of the comment as filed (target, file, quote, verdict, …)
    review: reviews/inbox/review-u02-2026-10-20.json   # the review file it came from
    hash: <approval hash of the version the teacher saw>  # optional, from the review file's `files`
    stale: false                               # made on an older version of the file
    resolution: {status: open, note: null, commit: null}   # open | fixed | answered | declined | owner | noted
```

`answered`, `declined` and `owner` resolutions need a `note` for the teacher. `review-import` files an OK verdict with no comment and no suggestion (an element marked OK, an answer adjudicated as wrong) as `noted`: nothing to do. `open` and `owner` comments are unresolved: they block the teacher's sign-off and the approval with `--signoff`. Each entry also records the `reviewer`.

### 4 · Back into the project

1. **Import:** `uv run content review-import review-u02-2026-10-20.json` (the owner, or an agent the owner asks) validates the file, checks every target (one unknown target, or a `file` that doesn't exist, and nothing is imported: tell the owner, don't guess), copies the file unchanged into `reviews/inbox/` (keeping its name, made safe; `-2`, `-3`… when another file has it), flags comments made on an older version as `stale` (the file's hash in the review differs from the current one; the worklist also says whether the element itself changed), and appends the comments to the ledger `reviews/u02.yaml` with `resolution: {status: open}` (or `noted`). A comment whose `id` is already in a ledger isn't filed again, so importing the same file twice changes nothing. Files in `reviews/inbox/` are the teacher's words: agents never edit them (a hook blocks it).
2. **Fix:** an agent works through the ledger with the `content-review` skill. For each open comment it edits the draft, then records `resolution: {status: fixed | answered | declined | owner, note, commit}`. Answer-key comments add accepted alternatives or near-misses; they never silently change a model answer. Suggestions that would break the level gate are declined with the reason and an alternative. Decisions about scope, story facts or register go to the owner (`status: owner`). Comments on approved files wait until the owner runs `content reopen`.
3. **Check:** `make annotate`, `make check-content`, then the content-critic on the changed files.
4. **Return:** `content review-export --unit u02 --since` produces the next page. The loop repeats until the teacher signs off.
5. **Approve:** the owner runs `uv run content approve <file> --by "<teacher>" --signoff reviews/inbox/<signed review>.json`. Because the sign-off carries the file hashes, the approved text is exactly the text the teacher signed. The command refuses when the review isn't filed in `reviews/inbox/` (import it first), has no `signoff`, is signed by someone other than `--by`, doesn't cover the file or covers an older version of it (a stale sign-off), or while any ledger has an `open` or `owner` comment on the file.

**Answer adjudication (M8.3).** `review-import` turns every unresolved answer-key decision in the scope's ledger into a proposal in `build/reports/review/<scope>-answers.{md,json}`: *accept* adds the answer as an alternative of the exercise's pattern (a recall `answer`, a cloze gap, or the chosen intent's `accept` list of a conversation turn) without changing the model answer (a whole-pattern `{…|…}` group gets one more alternative, anything else becomes `{<old>|<answer>}`; the answer is escaped); *near* adds a `near` entry with the teacher's hint; *wrong* changes nothing. "This should be accepted" comments from the app (category `answer-key`, verdict `change`, a `response`) are proposals to accept. A proposal says when the answer is already accepted, when a decision needs a person (an intent to choose, a format without a pattern) and when the file is approved, in which case the owner reopens it first; `itcontent.adjudication.apply_proposal` applies a pattern replacement and refuses approved files. The agent applies the rest by hand, runs the checks and resolves the comment.

`reviews/<scope>.yaml` is the audit trail: who said what about which version, and what was done about it. `content report` lists open comments per unit.
