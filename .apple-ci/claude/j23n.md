# j23n: shared rules

These rules hold in every j23n repository. They come from j23n/apple-ci (`claude/j23n.md`), and each repository keeps a copy in `.apple-ci/claude/`. Don't edit the copy: change apple-ci, then refresh it with `make update-apple-ci`, or with `claude/update.sh` in a repository without apple-ci's Makefile rules. Where the repository's own CLAUDE.md disagrees with this file, the repository's file wins.

## Language

- Write in US English: code, comments, docs, commit messages, issues and pull requests.
- Write plainly, in short sentences, for a reader who wasn't there. Say what is true now. Don't add history, hype or filler.
- Use the code's names for things, and use one name per thing.
- Follow the project's writing style guide if it has one.

## Commits

- Keep commits small and focused, one change each.
- The subject says what the change does, in the imperative, in at most 72 characters. The body says why, when that isn't obvious.
- Write each message so a reader can understand it from the message and the diff alone. Don't refer to a conversation, a session or a review round.
- A commit that works toward an issue carries a `Part of #N` line in its body. Never write "Closes", "Fixes" or "Resolves #N" in a commit. The pull request's description closes the issue (see "Pull requests").

## Branches

- Name a branch after its work, in a few lowercase words joined by hyphens, such as `menu-bar-today-list`. Don't use personal names or generated suffixes.
- Work reaches `main` through a pull request, unless the owner asks for a direct push.

## Issues

Write issues for whoever picks them up, often Claude, working from the issue alone, and for the owner, who decides what gets done. Keep them short.

The title says what's wrong or what should change, in at most 72 characters, such as "Week view draws short entries past their end". Don't repeat the app's name or the kind; labels carry those.

Every issue has exactly these three sections:

```markdown
## Problem

What's wrong or missing, and who it affects. For a bug: the steps to reproduce, what's expected and what happens.

## Proposal

What should change. For a bug, what correct looks like; leave the fix to whoever picks it up unless it's known.

## Acceptance criteria

- [ ] What done means, one checkable item each, including a test that fails today where one can.
```

- **Problem:** describe the behavior, not a guess at its cause. Point to the files or types to look at as hints, and say when you haven't verified them.
- **Proposal:** for an idea, give the change and any open questions, and name the docs or decisions it would change.
- **Labels:** the kind (`bug`, `enhancement`, `content` or `question`) and, when known, the size go in labels, not in the text.
- **Relations:** link issues with GitHub's metadata. Break a large issue into sub-issues, and mark one issue as blocked by another, instead of listing issue links or checklists of issues in the body. Before you open an issue, search for an existing one (`gh issue list --search`).
- **Privacy:** most j23n repositories are public. An issue never holds personal data, real values from someone's data, secrets, or a screenshot that shows any of them.
- **Decisions:** when an issue needs a decision from the owner, ask in a comment on the issue and wait. Don't guess.
- **Closing:** an issue closes through the pull request that finishes it. When you close one by hand, give the reason (not planned, or a duplicate of #N) in a comment.

## Pull requests

Write pull request descriptions for a human reviewer who wants the big picture. Keep them short.

The title says what the change does, in the imperative, in at most 72 characters.

Every description has exactly these three sections:

```markdown
## What and why

One paragraph: the motivation and what the change does about it.

## Changes

- A list of the actual changes, one item per change.

## Testing

How a human can see the change working.
```

- **Changes:** add a Mermaid diagram when it makes the changes clearer, and skip it when it doesn't.
- **Testing:** say what to run, open or look at to see the change working, such as a command, a screen or an output. Don't list test suites or say that tests pass; CI shows that.
- **Opening:** open the pull request yourself with `gh pr create`. That includes Claude on GitHub: open it there too, instead of posting a "Create a PR" link.
- **Issue links:** link issues in the description, at the end of "What and why". Write `Closes #N` for the issue the pull request finishes; GitHub closes that issue when the pull request reaches the default branch. Write `Part of #N` for an issue it only works toward, which stays open.
- **Stacks:** in a stack, only the layer that finishes the issue says `Closes #N`; the others say `Part of #N`. The `gh stack` metadata carries the stack's structure, so don't mention the stack, its layers or neighboring pull requests in a description.

## Secrets

- Never commit or print tokens, API keys, passwords or signing files, and don't read `.env` files.
- Secrets live in GitHub's Actions secrets, the Keychain, or gitignored local files that the owner fills in.
